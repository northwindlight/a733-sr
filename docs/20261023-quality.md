# 2026-10-23：1080p MMD → 4K 的涂抹感修复

## 问题与边界

用户反馈高清 MMD 成片比原片更糊、有塑料感。原任务为 1920×1080 → 3840×2160，
AnimeJaNai HD V3 UltraCompact 全模型输出，6811 帧，原处理约 2 小时。
此前的 540p 样片、后端数值一致性与音画完整性检查没有覆盖这一画质场景。

重新获取相同下载档、比较同一画面的原片 / 编码前 NPU 输出 / 最终成片：
模型会重绘、平滑原有细发丝和阴影纹理。更大 Compact 的局部参考结果也不能证明
换大模型就能解决这条 MMD 的问题。另发现一个独立的色彩错误：输出使用 BT.601 系数，
VE 编码的 VUI 却标为 BT.709。原片本身为 BT.709。

原下载档 HEVC 视频流约 0.606 Mbps，原成片 H.264 约 20.60 Mbps。
码率不能跨编码器直接当作画质评分；单纯加输出码率也不能补回模型改写的纹理。
因此本次保留现有 NBG，改为可调保真混合，并修复色彩转换。

## 新行为

- 网页和 API 新增 `strength=auto|0..1`。自动对源高度 ≥720 使用 0.35，其余使用 1.0。
  网页提供自动 / 35% / 65% / 100%。任务记录保存最终强度、锐化、色彩矩阵、源编码与码率。
- 模型比例为 `round(strength*256)/256`，其余来自原图 Catmull-Rom bicubic 放大。
  RGB 域混合先于色彩转换和可选锐化。降低 AI 比例会保留更多原图纹理，也会保留压缩痕迹。
  这是对原片更保真的选择，不等于恢复出了真实 4K 细节，也不保证任何素材都比原片好看。
- 双三次在 GPU 上分水平 / 垂直两级，使用有符号定点中间缓冲；CPU 回退使用同样的定点规则。
  不把整帧混合与插值工作转回 CPU。单遍原型太慢，最终改为可分离实现。
- 输入 NV12 的矩阵根据 ffprobe 选择 BT.709 或 BT.601；未标记沿用 BT.601。
  软件解码输入是 ffmpeg 已转换的 GBR。输出明确使用 BT.709，与 VE 编码标记一致。
  独立 `srpipe` 的矩阵默认仍为旧 BT.601，Web 流水线显式传入输出 BT.709。
- 字幕保护仍是明确的底部区域亮度保护；无字幕素材可以关闭。
- 本次没有覆盖旧成片；设置改变只影响新任务。

## 验证

`tools/qualitycheck.py` 在 A733 上通过：

- 0% AI 的结果与独立浮点 Catmull-Rom 参考相比，最大误差 1/255。
- BT.601、BT.709 的亮度 / 色度，与 ffmpeg 色彩参考相比最大误差均为 1/255。
- GBR 与带补齐行的 NV12，601→601 / 709→709 / 601→709，0% / 35% / 100%：
  CPU 与 GPU 结果逐字节一致；BT.709 CPU/GPU 抠块一致。
- 非数字、NaN、越界强度与非法矩阵被拒绝。

原 `tools/boardcheck.py`、`tools/gatetest.py` 全部通过，保留旧 CLI 行为与输出闸门。
Python / JavaScript 语法、`git diff --check` 通过。

真实 1080p 片段经过原尺寸完整分块后输出 4K，强制 `SR_CHUNK_FRAMES=17` 验证跨段：

| 输入 | 输出实际帧数 | 视频 | 音轨 |
|---|---:|---|---|
| FFV1 无损裁片，30 帧 | 30 | 3840×2160、30 fps、1.000 秒、BT.709 | 无 |
| H.264 带声音裁片，30 帧 | 30 | 3840×2160、30 fps、1.000 秒、BT.709 | 存在，1.000 秒 |

FFV1 测试片没有容器 nb_frames，任务起初的帧数来自时长估算；验收使用 ffprobe 解码计数。
未把容器估算值当作准确的原片帧数。带声测试的总耗时含排队，不用它比较吞吐。

单帧 1080p→4K：NPU 约 754 ms，GPU 保真混合与转换约 454 ms（可与下一帧 NPU 并行）。
单次 30 帧 FFV1 完整测试用时约 33.5 秒；仅为短片测量，不能外推为所有素材的固定速度。
